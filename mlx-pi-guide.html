Run LLMs Locally with MLX + pi

Everything that gets downloaded, where it lives, what runs (and whether it’s a daemon), how to turn it on/off, and how pi talks to your model — end to end.

0The big picture in one breath

You install two programs once, globally. Then for each session you start one background server and point your agent at it.

⓪ Bootstrap once
Run ./bootstrap.sh to install uv. After that, one tool — ./mlx-pi — does everything else.
① Install once
MLX (the inference engine) + pi (the coding agent / harness). Done by ./mlx-pi setup.
② Turn on
Start the MLX server — a local web server that loads your model and speaks the OpenAI API. Done by ./mlx-pi up.
③ Use
Launch pi; it sends prompts to http://localhost:8080/v1 instead of the cloud. Done by ./mlx-pi pi.
④ Turn off
Stop the server to free your RAM. Done by ./mlx-pi down.
💡 Nothing here phones home. Once a model is downloaded, you can run fully offline — no API keys, no token costs, no data leaving your Mac.

🧩 Why two files (bootstrap.sh + mlx-pi)?

bootstrap.sh is a ~5-line shell script whose only job is to install uv. It must be shell because a fresh Mac ships neither uv nor a reliable python3 — and bash is the one thing always present.

mlx-pi is a single Python program that does everything else (setup, server control, config, Hugging Face size checks). Its first line — #!/usr/bin/env -S uv run --script — tells uv to run it, and an inline metadata block lists its dependencies (rich, httpx). uv builds that environment automatically on first run and caches it; there’s no virtualenv to manage. Native JSON, HTTP, and arg-parsing make it far easier to read and extend than shell.

1The pieces — what each one is

Four moving parts. Two are tools you install; two are processes/files that exist at runtime.

install once

🧰 uv

A single fast binary that manages Python tools. We use it instead of pip. Crucially, uv tool install installs a command-line app into its own isolated environment but exposes it globally — so MLX works from every project without polluting any of them.

Lives at ~/.local/bin/uv.

install once

⚙️ MLX / mlx-lm

MLX is Apple’s array framework, purpose-built for Apple-Silicon unified memory and the M5’s Metal-4 tensor accelerators. mlx-lm is the package on top that runs LLMs and ships the CLIs you’ll actually call: mlx_lm.server, mlx_lm.generate, mlx_lm.chat.

Installed by uv into ~/.local/share/uv/tools/mlx-lm; commands symlinked into ~/.local/bin.

install once

🤖 pi

Mario Zechner’s bring-your-own-key coding agent (@earendil-works/pi-coding-agent). A minimal four-tool core — Read, Write, Edit, Bash — that talks to any OpenAI-compatible endpoint. That’s the hook we use to point it at MLX.

Installed via npm (needs Node). Config in ~/.pi/agent/models.json.

runs in background

🌐 The MLX server

When you run mlx_lm.server, it loads your model into memory and listens on http://localhost:8080, exposing OpenAI-style routes (/v1/chat/completions, /v1/models). This is the only long-running process. It is a daemon you start and stop; it is not a system service and won’t auto-start on boot.

downloaded on demand

📦 The model weights

The actual neural-network file (e.g. Qwen3-Coder-30B-A3B-Instruct-4bit, several GB) is pulled from the Hugging Face mlx-community repo the first time it’s used, then cached forever.

Lives at
~/.cache/huggingface/hub
One-time?
Download is one-time per model. After that it loads from disk into RAM each time the server starts.

2Choosing a model on Hugging Face

Almost every model you’ll run lives on huggingface.co. The skill is reading a model’s name and card well enough to answer three questions: Is it MLX-ready? Will it fit in my RAM? Is it the right kind of model?

2.1 — You want the MLX format

A raw model on Hugging Face can be in several formats. For Apple Silicon you want one already converted to MLX — not GGUF (that’s for llama.cpp/Ollama) and not raw PyTorch safetensors (unconverted).

SignalWhat it means
Org is mlx-community or lmstudio-community (…-MLX-…)✅ Pre-converted, loads directly with mlx_lm.
Name/files say MLX or repo has model.safetensors + config.json with an mlx quant section✅ MLX-ready.
Files end in .gguf❌ GGUF — for llama.cpp/Ollama, not mlx_lm.
Original org (e.g. google/…, Qwen/…) with no MLX note⚠️ Unconverted. Either find the mlx-community mirror, or convert it yourself (below).
Shortcut: browse the mlx-community org or search Hugging Face for <model name> mlx 4bit. If no MLX build exists, convert one once: 
mlx_lm.convert --hf-path Qwen/Qwen3-4B-Instruct -q

2.2 — Decoding the model name

Names look cryptic but are highly structured. Take the default:

mlx-community / Qwen3-Coder-30B-A3B-Instruct-4bit
└──── org ────┘ └─fam─┘ └role┘ └sz┘ └MoE┘ └─tune──┘ └quant┘
PartExampleMeaning
Orgmlx-communityWho published it. mlx-community = community MLX conversions.
Family / versionQwen3, gemma-4, Llama-4The base model and generation.
SpecializationCoder, VisionTuned for a domain (coding, vision…). Absent = general purpose.
Total size30B, 26b, 4BTotal parameters in billions — the headline number for capability and disk size.
Active size (MoE)A3B, A4B“Active” params per token in a Mixture-of-Experts model. A 30B-A3B model has 30B total but only ~3B compute per token → fast like a 3B, smart like a 30B. RAM tracks total; speed tracks active.
TuningInstruct, it, ChatInstruction/chat-tuned — what you want for an agent. A bare base model (no suffix) just autocompletes.
Quantization4bit, 8bit, bf16Precision of the weights (next section).

2.3 — Understanding quantization

Quantization shrinks each weight from 16 bits to fewer, trading a little quality for big memory savings. It’s the single biggest lever on whether a model fits.

TagBits/weightMemory vs fullUse when
bf16 / fp16161× (baseline)Max quality, you have RAM to burn, or fine-tuning.
8bit / Q88~½Near-lossless; great if it fits.
4bit / Q44~¼✅ The sweet spot for local use — big quality, fits most Macs.
3bit / lower≤3<¼Squeeze a model that otherwise won’t fit; quality starts to slip.

You may also see QAT (quantization-aware trained — better quality at low bits) and mixed-precision variants like OptiQ (sensitive layers kept at 8-bit, rest 4-bit). Both are fine; default to plain 4bit unless a card tells you otherwise.

2.4 — Will it fit in memory? (the rule of thumb)

Approx RAM to load = (total params in billions) × (bits ÷ 8) GB, then add ~20–30% headroom for context + the OS.

30B @ 4-bit
30 × 0.5 = ~15 GB weights → budget ~18–20 GB. ✅ on 32 GB.
26B @ 4-bit (Gemma)
≈ 15.6 GB on disk → budget ~20 GB. ✅ on 32 GB.
70B @ 4-bit
70 × 0.5 = ~35 GB → budget ~45 GB. Needs 64 GB.
4B @ 4-bit
≈ 2.5 GB → trivially fits 16 GB.
For MoE models, size against total params (the model is fully resident in RAM); the A#B active count only affects speed, not memory. Apple Silicon’s unified memory is shared with the GPU, so a model that “fits” still needs room left for your apps — leave a comfortable margin.

Tip: a model card on Hugging Face shows exact file sizes under “Files and versions” — sum the .safetensors shards for the real on-disk/in-RAM number, which beats any estimate.

2.6 — The script checks size before downloading

Neither script ever pulls weights without telling you the cost first. Before any download, it queries the Hugging Face API for the exact file sizes, prints the download size + a rough RAM estimate, warns if it exceeds your memory, and waits for a y/N confirmation (default No). If the model is already cached, it skips straight through. Use -y/--yes to bypass the prompt for automation.

# Example of what you'll see when a model isn't cached yet:
ℹ️  Querying Hugging Face for the size of: mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit
📦 Download size : ~16.0 GB   (to ~/.cache/huggingface/hub)
🧠 RAM to run    : ~20 GB     (rough estimate; you have 32 GB)
❓ Download this model (~16.0 GB) now? [y/N]

4Step by step — exactly what each command does

These are the raw commands ./mlx-pi setup (steps 1–4) and ./mlx-pi up / pi (steps 5–6) run for you. Shown here so you understand every line.

1

Install uv

one-time Downloads a static binary; touches no system Python.

curl -LsSf https://astral.sh/uv/install.sh | sh
# installs to ~/.local/bin and adds it to your shell PATH
2

Install MLX globally as a uv tool

one-time Creates an isolated env for mlx-lm but exposes its CLIs everywhere — the “install globally, use across projects” behavior you want. (mlx-lm pulls in mlx automatically.)

uv tool install mlx-lm
# later, to update:  uv tool install --upgrade mlx-lm
# verify:
mlx_lm.server --help
Why uv tool and not uv pip / a venv? uv tool is for applications you run by name (like pipx). One global copy, always on PATH, zero per-project setup.
3

Install pi (the harness)

one-time Needs Node; install via Homebrew or nodejs.org if missing.

brew install node            # if you don't have Node
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
🔒 --ignore-scripts is the latest recommended install: pi needs no post-install scripts, so skipping them is faster and avoids running arbitrary lifecycle scripts during install.
4

Tell pi about your local server

one-time Register a provider named local-mlx in ~/.pi/agent/models.json. The apiKey is required by the OpenAI client but ignored by MLX — any string works.

{
  "providers": {
    "local-mlx": {
      "baseUrl": "http://localhost:8080/v1",
      "api": "openai-completions",
      "apiKey": "local-mlx-no-key-needed",
      "models": [
        {
          "id": "mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit",
          "input": ["text"],
          "contextWindow": 131072,
          "maxTokens": 8192
        }
      ]
    }
  }
}
5

Start the MLX server

background daemon The first run downloads the model (several GB) into the HF cache, then loads it into memory and starts serving. Subsequent starts just load from disk.

mlx_lm.server --model mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit \
              --host 127.0.0.1 --port 8080
# health check (in another terminal):
curl http://localhost:8080/v1/models
⚠️ This holds the model in RAM the whole time it runs. A 30B 4-bit MoE uses roughly ~18–20 GB. Stop the server (next section) when you’re done to reclaim memory.
6

Run pi against it

interactive Launch pi, then pick the local-mlx model.

pi
# inside pi:  /model   → choose  local-mlx

6Turning it on and off

Only the server is stateful. ./mlx-pi wraps start order, a health-wait, and clean shutdown.

🟢 ON

./mlx-pi up      # start + wait healthy
./mlx-pi pi      # up (if needed) + launch pi
./mlx-pi status  # running? healthy?

🔴 OFF

./mlx-pi down    # stop, free RAM
./mlx-pi restart # reload model
./mlx-pi logs    # watch output
The server runs in the background and survives closing the terminal (its PID is tracked in ~/.mlx-pi/server.pid, logs in ~/.mlx-pi/server.log). By default it does not auto-start on reboot — start it when you want it. To change that, see the next subsection.

6.1 — Optional: run the server at startup (launchd)

macOS starts background user programs with launchd via small .plist files in ~/Library/LaunchAgents. ./mlx-pi plist generates a personalized one (your real home dir, model, and port already filled in) but does not install it — you opt in with the steps below.

⚠️ A launchd server is always on: it loads the model into RAM at login and reloads if it crashes. Great for a dedicated machine; less ideal on a laptop where you want that memory back. Prefer the small default model here, or stick with manual ./mlx-pi up/down.

Step 1 — generate the plist

./mlx-pi plist                 # default model + port 8080
./mlx-pi plist --qwen-coder    # serve the coder model at login
# → writes com.mlx-pi.server.plist with absolute paths baked in

Step 2 — install & enable

# copy into the per-user LaunchAgents folder
cp com.mlx-pi.server.plist ~/Library/LaunchAgents/
# load it (also starts it now because RunAtLoad=true)
launchctl load ~/Library/LaunchAgents/com.mlx-pi.server.plist
# confirm it's registered (look for com.mlx-pi.server)
launchctl list | grep mlx-pi
# verify it's actually serving
curl http://localhost:8080/v1/models

Step 3 — manage / disable later

# stop + unregister (won't start at next login)
launchctl unload ~/Library/LaunchAgents/com.mlx-pi.server.plist
# remove entirely
rm ~/Library/LaunchAgents/com.mlx-pi.server.plist
# logs from the launchd-managed server:
tail -f ~/.mlx-pi/launchd.err.log
To change the model/port later, re-run ./mlx-pi plist with new flags, then launchctl unload + load again. The manual ./mlx-pi up/down commands still work, but don't run both at once on the same port.

7The pi ↔ MLX integration, precisely

ConcernHow it works
TransportPlain HTTP to http://localhost:8080/v1. pi’s openai-completions API type speaks the OpenAI wire format, which mlx_lm.server implements.
Which modelThe id in models.json must match the model the server loaded (--model). Mismatch → pi asks for a model the server doesn’t have.
API keyRequired field, ignored by MLX. Use any non-empty placeholder.
Switching modelsInside pi: /model. To serve a different model, restart the server with a new --model and add a matching entry to models.json.
Toolspi runs Read/Write/Edit/Bash locally on your machine; only the chat/tool-call messages go to the model. Pick a tool-use-capable model (the Qwen3-Coder default is).

8Cheat sheet

Setup (run once)

./bootstrap.sh                  # install uv (once)
./mlx-pi setup                  # install + small default model
./mlx-pi setup --qwen-coder     # preset: Qwen3-Coder 30B
./mlx-pi setup --gemma          # preset: Gemma 4 26B (text+image)
./mlx-pi setup --prefetch        # download now (asks: size? [y/N])
./mlx-pi setup --model <hf-repo-id>
./mlx-pi --help

Daily driving

./mlx-pi up                  # small default model
./mlx-pi up --qwen-coder     # serve the coder model
./mlx-pi up --gemma          # serve Gemma instead
./mlx-pi pi
./mlx-pi down
./mlx-pi status --help

Quick manual tests

mlx_lm.chat                 # REPL, no server
mlx_lm.generate --prompt "hi"
curl localhost:8080/v1/models

9Troubleshooting

SymptomFix
uv: command not found when running ./mlx-piRun ./bootstrap.sh first (it installs uv), then open a new terminal.
First ./mlx-pi run pauses a few secondsNormal — uv is building the script's dependency env (rich, httpx). It's cached after that.
mlx_lm.server: command not foundOpen a new terminal so PATH refreshes. fish users: fish_add_path ~/.local/bin.
pi hangs on first messageServer is likely still downloading the model. Watch ./mlx-pi logs; the up command waits for health for you.
Out of memory / system sluggishModel too big for your RAM. Use a smaller one (see table) and close other heavy apps.
pi can’t reach the modelConfirm the server is up: curl localhost:8080/v1/models, and that the id in models.json matches --model.
Port already in useRun the server on another port: ./mlx-pi up --port 8090 and re-run ./mlx-pi setup --port 8090 to update baseUrl.
